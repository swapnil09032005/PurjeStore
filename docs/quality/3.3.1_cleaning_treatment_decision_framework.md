## 1. Purpose

This document defines the evidence-based framework used to decide how candidate data-quality findings will be treated during PurjeStore cleaning.

The framework deliberately separates:

1. anomaly detection,
2. treatment decision, and
3. actual value modification.

A quality signal does not automatically justify changing the data. Treatment must be supported by available evidence and established field meaning.

## 4. Treatment Vocabulary

The approved treatment vocabulary contains eight categories:

| Treatment | Meaning |
|---|---|
| `KEEP` | Preserve the field/value representation because evidence supports retention. |
| `NORMALIZE` | Standardize representation without changing underlying business meaning. |
| `CONVERT` | Convert to an appropriate technical representation when semantic meaning is established. |
| `MASK` | Protect sensitive information while retaining an analytically useful representation where justified. |
| `EXCLUDE` | Exclude a field/value from a particular analytical dataset when appropriate for that analytical purpose. |
| `QUARANTINE` | Isolate a value/record from normal analytical processing pending investigation. |
| `IMPUTE` | Replace missing values using a justified, evidence-supported method. |
| `LEAVE_UNRESOLVED` | Make no transformation because evidence is insufficient to justify one. |

These categories are decision vocabulary, not automatic cleaning rules.

---

## 5. Core Decision Principle

> A detected quality signal does not by itself justify changing the data.

Treatment must consider:

- field semantics,
- relationship evidence,
- temporal evidence,
- identity evidence,
- observed value patterns,
- missingness context,
- and validated findings from earlier milestones.

When evidence is insufficient, the conservative treatment is:

`LEAVE_UNRESOLVED`

This prevents unsupported business assumptions from being encoded into the cleaned data.

## 6. Decision Hierarchy

### Rule 1 — Authoritative resolution

If a field has a validated authoritative workflow disposition from Milestone 3.2.7-C-F:

**Treatment → `KEEP`**

This covers:

- `TRUE_TRANSITION_HISTORY_CONFIRMED`
- `SNAPSHOT_STATE_ONLY`
- `REPEATED_ENTITY_FALSE_HISTORY_GROUPING`

Workflow/state information is not treated as generic dirty data.

### Rule 2 — Validated identity evidence

If validated identity evidence establishes the field's role:

**Treatment → `KEEP`**

Identifiers are not modified merely because they repeat.

### Rule 3 — Semantic-review-only evidence

If a field is only in the workflow semantic-review queue and lacks authoritative resolution or validated identity evidence:

**Treatment → `LEAVE_UNRESOLVED`**

A review flag means additional interpretation may be needed; it does not authorize modification.

### Rule 4 — Missingness-only evidence

If a field has missingness evidence but no authoritative workflow resolution or validated identity evidence:

**Treatment → `LEAVE_UNRESOLVED`**

Missingness alone does not authorize:

- deletion,
- imputation,
- replacement,
- or exclusion.

### Rule 5 — Insufficient evidence

If no validated rule supports a transformation:

**Treatment → `LEAVE_UNRESOLVED`**

## 7. Missingness Treatment

The evidence contains:

- 205 fully missing fields
- 388 high-missingness fields
- 61 extreme-missingness fields

High missingness is a quality signal, not proof of bad data.

Missingness can represent:

- optional attributes,
- non-applicable fields,
- event-dependent attributes,
- workflow-specific attributes,
- historical capture differences,
- or genuinely missing information.

Therefore:

- no field is automatically deleted because it is fully missing;
- no value is automatically imputed because missingness is high;
- no placeholder is automatically replaced without semantic evidence.

Actual imputation or exclusion decisions belong to later treatment mapping.

---

## 8. Workflow and Status Treatment

Workflow fields require semantic caution because apparent state changes may represent:

- genuine historical transitions,
- snapshot states,
- repeated-entity grouping,
- same-state repetitions,
- timestamp ties,
- or same-timestamp state changes.

### 8.1 Confirmed transition histories

Fields classified as `TRUE_TRANSITION_HISTORY_CONFIRMED` are retained.

The observed transitions are part of the source's temporal meaning.

### 8.2 Snapshot-state fields

Fields classified as `SNAPSHOT_STATE_ONLY` are retained.

A snapshot state must not be converted into an artificial historical sequence.

### 8.3 False-history grouping fields

The three validated false-history grouping fields are retained:

- `product_bulk_uploads.status`
- `product_bulk_uploads.preview_data`
- `wallet_withdrawal_requests.status`

The conclusion is about incorrect history reconstruction through an inappropriate repeating entity/grouping key, not about deleting the fields.

## 9. Identifier Preservation

Repeated identifiers are not automatically duplicates.

Identifier interpretation must consider:

- table role,
- key role,
- uniqueness,
- relationship evidence,
- business entity grain,
- and cross-table evidence.

Therefore:

- repeated IDs are not automatically deduplicated;
- foreign keys are not altered merely because they repeat;
- candidate identifiers are not converted to categories merely because they have few distinct values;
- identifiers with validated roles are preserved.

This protects the relational meaning of the recovered database.

## 16. Limitations

### 16.1 `LEAVE_UNRESOLVED` is not a final quality verdict

It means that the present evidence does not justify transformation. It does not mean that the field is necessarily clean or defective.

### 16.2 Current decisions are primarily field-level

Future cleaning may require:

- row-level decisions,
- value-level decisions,
- record-state decisions,
- analytical-dataset decisions,
- or business-process decisions.

These should not be inferred prematurely.

### 16.3 Analytical purpose affects treatment

A field can be retained in a master cleaned layer but excluded from a particular analytical dataset because it is unsuitable for that dataset's grain or purpose.

Therefore:

`KEEP` does not mean "use in every downstream dataset."

### 16.4 Missingness requires semantic interpretation

Before imputation, exclusion, or normalization, field meaning and analytical role must be established.

### 16.5 Workflow history depends on entity grain

The workflow investigation demonstrated that grouping by an inappropriate repeating foreign key can create false histories.

Downstream temporal analysis must therefore use validated business entity identity.

## 17. Boundary Between 3.3.1 and Actual Cleaning

This task establishes **what is currently justified**, not the complete physical cleaning operation.

Later treatment specification must determine, where applicable:

- whitespace normalization;
- category standardization;
- placeholder handling;
- datatype conversion;
- PII masking;
- invalid-value quarantine;
- missing-value imputation;
- analytical exclusion;
- or continued unresolved status.

Every transformation must have an evidence-backed reason.

Actual cleaned datasets must be written outside the raw source directory.

---

## 18. Decision Framework Summary

The intended pipeline is:

**Evidence signal**  
→ **Semantic interpretation**  
→ **Validated identity/workflow context**  
→ **Treatment decision**  
→ **Validation**  
→ **Separate cleaned output**

It is deliberately not:

**Anomaly detected**  
→ **Automatic value modification**

This conservative approach is important for recovered relational data because unusual values, repeated identifiers, state changes, missingness, and representation differences can have legitimate structural explanations.
