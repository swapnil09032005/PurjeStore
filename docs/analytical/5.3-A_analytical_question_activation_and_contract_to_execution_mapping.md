## 1. Purpose

Major Milestone 5.3-A translates the finalized analytical contracts produced in Major Milestone 5.2-D into execution-level specifications.

The purpose is to establish, for each approved analytical contract:

* the analytical question to be examined;
* the authoritative source grain;
* whether an explicit grain key is available;
* whether execution is source-only or relationship-dependent;
* how relationship requirements are represented at execution level;
* how grain preservation must be handled;
* whether construction requires additional semantic or relationship review;
* population, temporal, quality, and missingness limitations;
* and the appropriate construction decision.

This milestone is an **activation and execution-mapping milestone**, not an analytical dataset construction milestone.

---

## 2. Scope Boundary

5.3-A explicitly does **not**:

* construct analytical datasets;
* perform analytical joins;
* select final business KPIs;
* select ML targets;
* make causal claims;
* make business-impact claims;
* invent missing grain keys;
* override authoritative 5.2-D contract decisions;
* resolve deferred semantic or relationship questions without evidence.

The execution mapping therefore represents the controlled transition from finalized analytical contracts toward future purpose-specific construction review.

## 6. Grain Activation

### 6.1 Authoritative grain evidence

The 5.2-D register contains populated:

* `source_grain_statement`;
* `grain_validation`;
* `grain_specification_status`.

All 26 contracts contain these fields.

The execution mapping therefore requires these fields to remain populated.

### 6.2 Explicit grain keys

The majority of the contracts contain an explicit `grain_key_candidate`.

These are classified in 5.3-A as:

`EXPLICIT_GRAIN_KEY_SPECIFIED`

The execution mapping preserves those authoritative grain keys without modification.

### 6.3 Source-record-grain exceptions

Exactly three contracts have a blank `grain_key_candidate`:

1. `daily_category_metrics`
2. `daily_platform_metrics`
3. `daily_vendor_metrics`

For all three contracts, the authoritative 5.2-D evidence states:

> One row per source record; business grain not independently established.

Their authoritative grain validation is:

`SOURCE_GRAIN_REQUIRES_SEMANTIC_REVIEW`

Their authoritative grain specification status is:

`SOURCE_GRAIN_SPECIFIED`

These contracts are therefore classified as:

`SOURCE_RECORD_GRAIN_SEMANTIC_REVIEW_REQUIRED`

The blank grain keys are intentionally preserved.

No identifier was invented to make the grain key field non-blank.

### 6.4 Grain preservation rule

For explicit grain-key contracts:

`PRESERVE_EXPLICIT_SOURCE_GRAIN_KEY`

For the three source-record-grain contracts:

`PRESERVE_SOURCE_RECORD_GRAIN_NO_BUSINESS_KEY_INVENTED`

This preserves the distinction between a known source grain and an independently established business key.

## 7. Relationship Execution Mapping

5.3-A translates the authoritative 5.2-D `relationship_required` information into execution-level semantics.

The raw 5.2-D field does not need to be duplicated into the execution mapping because the execution mapping represents its meaning through:

* `validated_relationship_required`;
* `execution_mode`;
* `relationship_evidence_status`;
* `relationship_specification`;
* `join_execution_status`;
* `aggregation_before_join_status`.

### 7.1 Source-only execution

Contracts whose current source contract does not require a relationship-dependent execution path are classified as:

`SOURCE_ONLY`

For these contracts:

`validated_relationship_required = False`

and:

`join_execution_status = NO_JOIN_REQUIRED_AT_5_3_A`

### 7.2 Relationship-dependent execution

Contracts requiring relationship-dependent execution are represented as:

`RELATIONSHIP_DEPENDENT`

For these contracts:

`validated_relationship_required = True`

and actual joining is deferred to purpose-specific construction.

The mapping therefore records the execution requirement without performing the join.

### 7.3 Fan-out protection

Where a relationship-dependent execution path may create fan-out, the execution mapping records:

`REQUIRED_ONLY_IF_PURPOSE_SPECIFIC_JOIN_PATH_CREATES_FANOUT`

for aggregation-before-join consideration.

This does not claim that a fan-out has occurred in 5.3-A.

It establishes a controlled execution rule for future construction.

## 8. Construction Decisions

5.3-A does not construct datasets.

Instead, each contract receives an execution-level construction decision.

The principal decision categories are:

### `ELIGIBLE_FOR_PURPOSE_SPECIFIC_CONSTRUCTION_REVIEW`

The contract has a complete specification and does not currently require the grain-semantic exception handling or relationship-dependent construction review that would prevent progression to purpose-specific construction review.

### `DEFER_CONSTRUCTION_PENDING_GRAIN_SEMANTIC_REVIEW`

This applies to the three source-record-grain contracts:

* `daily_category_metrics`
* `daily_platform_metrics`
* `daily_vendor_metrics`

Their source grain is known at the source-record level, but the business grain has not been independently established.

### `DEFER_CONSTRUCTION_PENDING_PURPOSE_SPECIFIC_RELATIONSHIP_REVIEW`

This applies where construction depends on a relationship path requiring purpose-specific validation before physical construction.

The construction decision is therefore deliberately conservative and evidence-driven.

## 13. Important Evidence-Based Exception

The three daily metrics contracts require explicit preservation of a semantic limitation.

They cannot be represented as having independently established business keys merely because the execution mapping requires a grain representation.

The evidence supports only:

* one row per source record;
* business grain not independently established;
* semantic review required.

Therefore, 5.3-A deliberately leaves the grain key blank for these contracts.

This is treated as an evidence-preserving limitation rather than a missing value to be artificially repaired.
