## 3. Analytical Dataset Definition

An analytical dataset is a purpose-built dataset designed to answer a defined analytical question while maintaining a clearly specified row-level meaning.

A valid analytical dataset requires:

- A defined analytical purpose.
- A clearly defined grain.
- A stable analytical key or key structure.
- Valid source relationships.
- Known join cardinality.
- Controlled aggregation.
- Valid measures.
- Relevant dimensions or attributes.
- Explicit inclusion and exclusion rules.
- Reproducible construction logic.
- Validation checks.
- Documented limitations.

A collection of joined tables is therefore **not automatically an analytical dataset**.

Analytical correctness depends on purpose, grain, relationships, cardinality, aggregation, measures, and validation.

## 4. Analytical Grain

The analytical grain defines the exact meaning of one row.

| Dataset type | Example grain |
|---|---|
| Customer dataset | One row = one customer |
| Product dataset | One row = one product |
| Order dataset | One row = one order |
| Order-line dataset | One row = one order line |
| Shipment dataset | One row = one shipment |
| Payment dataset | One row = one payment |
| Customer-month dataset | One row = one customer-month |
| Product-month dataset | One row = one product-month |

These are methodological examples only. They do not represent a decision that these datasets necessarily exist or should be constructed in PurjeStore.

## 5. Grain Integrity Rules

1. Every analytical dataset must have an explicit grain statement.
2. The grain must be specific enough to determine row identity.
3. The analytical key must be compatible with the declared grain.
4. Measures must be interpreted at the declared grain.
5. Joins must preserve or intentionally transform the declared grain.
6. Unexpected row multiplication must be treated as a validation issue.

## 6. Relationship Cardinality

| Cardinality | Meaning |
|---|---|
| 1:1 | One record in A corresponds to one record in B |
| 1:N | One record in A corresponds to many records in B |
| N:1 | Many records in A correspond to one record in B |
| N:N | Many records in A correspond to many records in B |

Relationship cardinality must be understood before joining datasets.

A database relationship that is technically valid is not automatically safe for analytical use.

## 7. Fan-Out Risk Validation

A controlled synthetic example was used to demonstrate fan-out.

- 1 order
- 2 order items
- 2 payments

Directly joining both one-to-many child tables to the order produced:

**2 × 2 = 4 rows**

for the single logical order.

This demonstrates why direct joins across multiple one-to-many relationships can multiply records and incorrectly inflate measures.

The result was successfully validated during notebook execution.

## 8. Aggregation Before Joining

The synthetic demonstration aggregated child-level information before joining it to the order-level dataset.

### Order items

- Item count
- Total item amount

### Payments

- Payment count
- Total payment amount

Both child datasets were reduced to the intended order grain before joining.

## 9. Controlled Join Validation

The safe analytical demonstration used explicit Pandas cardinality validation:

validate="one_to_one"

The resulting analytical demonstration contained one row and one unique order ID.

Therefore, the intended order-level grain was preserved.

## 16. Methodological Decisions

### Decision 1 — Grain must be explicit

No analytical dataset will be considered valid unless the meaning of one row is explicitly documented.

### Decision 2 — Cardinality must be validated

Relationships will not be treated as analytically safe merely because they exist in the source database.

### Decision 3 — Fan-out must be controlled

Multiple one-to-many relationships must not be joined directly when that would multiply the analytical grain.

### Decision 4 — Aggregate before joining when required

Child-level information must be reduced to the target analytical grain before joining to an analytical anchor where necessary.

### Decision 5 — Candidate datasets must be evidence-driven

PurjeStore will not automatically receive conventional datasets unless the actual recovered data supports them.

### Decision 6 — Raw data remains protected

No raw PurjeStore source data is modified during analytical dataset design.

### Decision 7 — ML is downstream of analytical design

Machine-learning feature construction must not begin until the analytical grain and supporting dataset architecture are validated.
